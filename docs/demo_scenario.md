# Сценарий демонстрации платформы HoneyForge

## Введение
Данный документ описывает пошаговый сценарий демонстрации возможностей платформы HoneyForge перед жюри и экспертами SOC:
1. Запуск платформы и динамическая генерация учетных данных без паролей по умолчанию.
2. Защита аутентификации: HTTP 429, временная блокировка (lockout) и RBAC.
3. Сетевая изоляция (DMZ vs MGMT) и маскировка телеметрии (Stealth 404).
4. Отказоустойчивость телеметрии (Store & Forward: остановка шлюза -> атака -> запуск -> дослылка без потерь).
5. Автоматизированная верификация правдоподобия (`scripts/selfcheck_realism.py`: 9/9 PASS).
6. Демонстрация «Внутри ловушки нет маркеров» (маскировка процессов, реалистичные хэши yescrypt, zero egress).
7. Мониторинг SOC, корреляция правил (AlertEngine) и экспорт IoC (STIX 2.1 / Suricata).

---

## Шаг 1. Запуск платформы и динамическая генерация секретов
1. **Генерация криптографических секретов**:
   ```powershell
   python scripts/gen_env.py
   ```
   **Что показать:**
   - Скрипт генерирует файл `.env` со случайными криптографически стойкими паролями операторов (`ADMIN_PASSWORD`, `ANALYST_PASSWORD`), токенами нод (`NODE_KEY_LOW`, `NODE_KEY_MED`) и JWT-секретом.
   - В репозитории отсутствуют рабочие пароли по умолчанию (`admin123` и т.д.).
   - Сгенерированные пароли операторов выводятся в консоль.

2. **Запуск стека контейнеров**:
   ```powershell
   docker compose up -d --build
   ```
3. **Проверка статуса сервисов**:
   ```powershell
   docker compose ps
   docker logs app-backend
   ```
   **Что показать:**
   - 7 сервисов успешно запущены и функционируют:
     - `db-store` (PostgreSQL 16, healthy)
     - `app-backend` (C2 сервер FastAPI, healthy)
     - `static-edge` (Nginx DMZ шлюз приёма телеметрии ловушек)
     - `mgmt-gateway` (Nginx Management шлюз оператора SOC)
     - `systemd-resolved-low` (Низкоинтерактивная ловушка DMZ)
     - `rsyslogd-med` (Среднеинтерактивная ловушка DMZ)
     - `sec-scanner` (Симулятор атак DMZ)

## Шаг 2. Защита аутентификации: 429 Lockout, RBAC и Logout (FR-C5)
1. **Демонстрация защиты от подбора паролей (Lockout & Rate-limit)**:
   Отправьте 5 неверных попыток авторизации подряд:
   ```powershell
   for ($i=1; $i -le 6; $i++) {
       curl -k -i -X POST "https://localhost/api/v1/auth/login" `
            -H "Content-Type: application/json" `
            -d '{"username":"admin","password":"wrongpassword"}'
   }
   ```
   **Что показать:**
   - На 6-й попытке сервер возвращает **HTTP 429 Too Many Requests** с телом:
     `{"detail": "Слишком много неудачных попыток. Аккаунт заблокирован на 5 минут."}`
   - В журнале аудита (`AuditLog`) фиксируются события `failed_login` и `account_locked`.

2. **Успешный вход администратора (`admin`)**:
   - Выполните вход в веб-интерфейс `https://localhost` с верным паролем из вывода `scripts/gen_env.py`.
   - Доступен полный функционал: управление профилями, запуск симулятора атак, изменение правил.

3. **Проверка ролевой модели (RBAC)**:
   - Выполните вход под учетной записью `analyst`.
   - В веб-интерфейсе элементы управления парком заблокированы.
   - Попытка прямого создания ловушки или вызова управляющего эндпоинта возвращает **HTTP 403 Forbidden**.

4. **Отзыв токена (Logout & JTI Denylist)**:
   - Нажмите кнопку «Выйти» (`POST /api/v1/auth/logout`).
   - Идентификатор `jti` токена помещается в denylist отозванных токенов.
   - Повторное использование этого токена немедленно отклоняется с кодом **HTTP 401 Unauthorized**.

5. **Безопасное подключение к WebSocket через одноразовый билет**:
   - UI запрашивает одноразовый билет через `POST /api/v1/auth/ws-ticket`.
   - Подключение происходит по URL `wss://localhost/ws/attacks?ticket=<single_use_ticket>`.
   - В логах Nginx query-параметры очищаются, предотвращая утечку учетных данных.

## Шаг 3. Сетевая изоляция и маскировка эндпоинтов (MASK-1...3)
1. **Проверка недоступности внутренних сервисов**:
   ```powershell
   curl -k http://localhost:8000
   curl -k http://localhost:5432
   ```
   **Что показать:**
   - Соединения отклоняются (`Connection Refused`). Порты 8000 и 5432 доступны только во внутренней сети `internal_mgmt`.

2. **Проверка Stealth Telemetry (MASK-2)**:
   Отправьте неавторизованный запрос на путь телеметрии:
   ```powershell
   curl -k -i -X POST "https://localhost/cdn-cgi/rum" -d '{"event":"test"}'
   ```
   **Что показать:**
   - Сервер возвращает стандартный **HTTP 404 `{"detail": "Not Found"}`**.
   - Ответ по статусу, HTTP-заголовкам (`Content-Length: 22`, `Content-Type: application/json`) и телу полностью неотличим от запроса к случайному несуществующему адресу (например, `https://localhost/random-path-12345`). Нарушитель не может определить наличие C2-эндпоинта сканированием.

## Шаг 4. Отказоустойчивость Store & Forward (FR-A4)
Данный шаг демонстрирует гарантированную доставку телеметрии при падении сети или шлюза:

1. **Остановка шлюза передачи данных**:
   ```powershell
   docker stop static-edge
   ```
   **Что показать:** Шлюз `static-edge` остановлен, прямая связь ловушек с C2 разорвана.

2. **Имитация атаки на ловушку во время аварии сети**:
   Выполните атаку на среднеинтерактивную ловушку SSH (порт 2222):
   ```powershell
   ssh -p 2222 -o StrictHostKeyChecking=no root@localhost
   ```
   (Введите любой пароль, введите пару команд).

   **Что происходит внутри ловушки:**
   - Агент фиксирует событие атаки, генерирует уникальный `event_uid`.
   - Попытка отправить телеметрию на `https://static-edge` завершается сетевой ошибкой.
   - Событие атомарно помещается в локальный SQLite буфер (`pending`). Ловушка продолжает бесперебойную работу.

3. **Восстановление шлюза**:
   ```powershell
   docker start static-edge
   ```

4. **Проверка автоматической дослылки (Flushing)**:
   - В течение следующего цикла синхронизации агент восстанавливает соединение со шлюзом.
   - Накопленные события пакетом передаются на сервер управления.
   - Сервер выполняет дедупликацию по `event_uid` и подтверждает прием.
   - В SOC Дашборде (`https://localhost`) мгновенно появляются все события, произошедшие в период аварии. **Потерь данных нет (0% Data Loss)**.

## Шаг 5. Автоматизированная верификация правдоподобия (`scripts/selfcheck_realism.py`)

- `[PASS] Пункт 02`: Правдоподобие ошибок bash и coreutils (GNU-форматы `cat`, `cd`, `rm`, `command not found`).

- `[PASS] Пункт 04`: Задержки сетевых рукопожатий и аутентификации (выборка N=10, stddev > 0, дисконнект SSH после 3 попыток).

## Шаг 6. Демонстрация «Внутри ловушки нет маркеров» (MASK-4, MASK-6)
Подключитесь к интерактивной сессии SSH ловушки:
```powershell
ssh -p 2222 -o StrictHostKeyChecking=no root@localhost
```
(Введите пароль `admin123` со второй попытки согласно политике приманки).

1. **Маскировка процессов (MASK-4)**:
   ```bash
   ps aux
   ```
   **Что видит атакующий:**
   - Список стандартных системных процессов Ubuntu: `systemd`, `rsyslogd`, `cron`, `sshd`.
   - Процесс ловушки замаскирован под `rsyslogd` (или `systemd-resolved`).
   - В выводе **отсутствуют** упоминания `python`, `fake_ssh.py`, `honeyforge`, `honeypot`.

2. **Чистота файловой системы и отсутствие симуляционных строк**:
   ```bash
   grep -riE "(fake|honeypot|honeyforge|decoy|mock|emulator)" /etc /proc /tmp
   ```
   **Что видит атакующий:**
   - 0 совпадений! Ни одного подозрительного маркера эмулятора.

3. **Реалистичные хэши паролей (/etc/shadow)**:
   ```bash
   cat /etc/shadow
   ```
   **Что видит атакующий:**
   - Современные хэши yescrypt формата `$y$j9T$...` (стандарт Ubuntu 22.04), уникальные для каждого пользователя (`root`, `deploy`, `ubuntu`). Никаких открытых паролей или шаблонных md5-хэшей.

4. **Симуляция сети без несанкционированного выхода (Zero Egress)**:
   ```bash
   curl http://example.com/miner.sh
   wget http://example.com/payload.bin
   ```
   **Что происходит:**
   - Команды выводят правдоподобный прогресс-бар загрузки, рассчитывают SHA-256 артефакта и логируют полезную нагрузку.
   - При этом ловушка **не совершает реальных сетевых подключений во внешнюю сеть** (zero egress), предотвращая использование ловушки для атак на третьи лица.

## Шаг 7. Мониторинг SOC, корреляция правил и экспорт IoC
1. Откройте вкладку «Лента атак» в дашборде:
   - Новые события отображаются в реальном времени с визуализацией гео-локации, ASN и классификацией по матрице MITRE ATT&CK.
2. Проверьте вкладку «Оповещения и правила»:
   - Срабатывание правила `brute_force` при серии неудачных попыток входа.
   - Срабатывание правила `honeytoken` при попытке чтения `/root/.aws/credentials`.
3. Экспорт индикаторов компрометации (IoC):
   - Скачайте IoC в формате **STIX 2.1 JSON** (`GET /api/v1/ioc/export/stix`).
   - Скачайте правила обнаружения в формате **Suricata NIDS** (`GET /api/v1/ioc/export/suricata`).
   - Скачайте выгрузку в формате **CSV** (`GET /api/v1/ioc/export/csv`).
